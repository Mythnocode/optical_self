# 重要 Bug 回归检查清单

本文件记录已经真实出现过、后续重构时不得重新引入的问题。它用于人工或半自动回归验收，不替代必要的底层逻辑检查。

## 使用原则

1. 先复现旧问题，再确认修复后的连续操作结果。
2. 优先验证用户真实操作路径，不只检查函数或接口是否存在。
3. 同时检查“操作后的当前状态”和“离开/返回页面后的状态”。
4. 重要状态必须由统一状态源驱动，页面不能各自猜测。
5. 页面文字、按钮状态和实际后台状态必须一致。
6. 新增重要 Bug 修复后，在本文件追加回归步骤；不为每个 UI Bug 单独堆叠易失真的测试代码。

## ML-STATE-001：设为当前模型后，模型分析主页仍显示“尚未选择”

### 旧问题

在“模型分析 → 训练与版本 → 模型版本”中选择已有模型并点击“设为当前模型”后：

- “选中模型”区域已经显示“已应用”；
- `current_model_id` 实际已经更新；
- 但返回/滚动到模型分析主页时，“当前模型”仍显示“尚未选择”，主图仍提示没有当前模型。

### 根因

`RegistryContext.current_model_changed` 原来只连接到模型版本区域的 `_select_model_by_id()`，没有连接到模型分析主页的 `_refresh_analysis()`。

因此“当前模型”状态已经改变，但主页没有收到刷新动作，形成同一页面内两套不同步的显示状态。

### 修复要求

当前模型发生变化时，模型分析主页必须同步刷新。当前模型被清空时也必须恢复为“尚未选择”，不能保留旧模型摘要。

### 回归步骤

1. 打开“模型分析”。
2. 打开“训练与版本 → 模型版本”。
3. 选择一个已有模型。
4. 点击“设为当前模型”。
5. 不切换页面，直接查看上方“模型摘要”。
6. 确认“当前模型”立即显示刚采用的模型，而不是“尚未选择”。
7. 确认测试 R²、MAE、RMSE 与该模型的独立测试指标一致。
8. 若模型 R² 较差，结论区应立即显示相应可靠性提示，而不是无模型提示。
9. 再切换到其他页面并返回“模型分析”，确认当前模型仍保持一致。
10. 若当前模型被显式清空，主页必须立即恢复“尚未选择”。

### 通过标准

- 模型版本区与模型分析主页读取同一个 `current_model_id`；
- 点击“设为当前模型”后无需刷新页面即可同步；
- 主图、模型摘要、可靠性结论使用同一个模型；
- 不允许出现“下方显示已应用、上方显示尚未选择”的状态分裂。

## UI-PROGRESS-001：进度条显示前端伪百分比或倒退

### 风险

提交任务以后，如果前端先人为写入 3%、5% 等“看起来在运行”的数值，用户会把它误认为后台真实进度；后台事件晚到或乱序时还可能出现进度倒退。

### 修复要求

- 尚未拿到后台 job_id / 可量化进度时，只显示不确定进度（忙碌条），不显示伪百分比；
- 拿到 job_id 后，百分比只能来自后端任务状态或 WebSocket 进度事件；
- 参数扫描、容差、数据集等批量任务的后端进度必须由“真实完成样本数 / 总样本数”计算；
- 前端使用单调进度跟踪，乱序事件不能让可见进度倒退；
- 失败、取消、完成都保留明确终态，不突然跳回 0%。

### 回归步骤

1. 在“参数研究”提交一次至少 7 点的扫描。
2. 提交请求尚未返回 job_id 时，确认进度区显示“正在提交后台…”而不是 3% 等数值。
3. 后端返回 job_id 后，观察任务中心/页面进度是否随真实完成点数增加。
4. 确认后端状态中的 `completed_items` 与 `total_items` 能对应到进度变化。
5. 完成时显示 100%；失败/取消时显示明确终态。
6. 生成数据集并重复上述检查，确认数据集页的进度条也由后台事件驱动。
7. 快速切换页面再返回，确认当前任务进度不会重置或引用另一个 job。

### 通过标准

- 没有前端定时器或硬编码百分比伪造后台进度；
- 批量任务进度与后台真实完成样本数一致；
- 同一 job 的可见进度单调不下降；
- 页面、任务中心和后台状态最终一致。

## UI-LAYOUT-001：字体缩小、控件尺寸与对齐在重构后重新分裂

### 修复要求

普通页面遵守统一布局标尺：页面边距 24 px、一级间距 24 px、卡片 16 px、紧密控件 8 px；普通控件高度 36 px、主要按钮 40 px。正文和辅助说明不得为了塞进一行而缩成难以投屏阅读的字号。

### 回归步骤

1. 在 1366×768、1920×1080 分别打开参数研究、模型分析、SHAP、仿真、任务中心。
2. 检查页面标题、卡片、主图区、表格的左右边界是否稳定。
3. 检查普通按钮/输入框高度是否一致，主要按钮是否有稳定视觉层级。
4. 检查标签与输入框是否在统一表单网格中对齐。
5. 检查正文、帮助文字、状态文字在 1366×768 和投屏截图中均可读，不以缩字号解决拥挤。
6. 运行 `tools/ui_layout_ruler.py` 对公共组件做集中视觉复核。

### 通过标准

布局差异来自任务需要，而不是页面各自随意设置 margin、字号和控件高度；不出现为了“塞下更多内容”而明显缩小字体的情况。

## DATASET-PHYSICS-001：数据集波长必须与当前方案一致

- **曾发生的问题**：平台项目把波长保存在 `source.wavelength_nm`，Headless 数据集生成器只读取顶层 `wavelength_nm`，字段缺失时静默回退到 1550 nm；界面显示 780 nm，但训练数据可能按 1550 nm 计算。
- **根因**：同一物理状态存在两种字段位置，数据集适配层没有使用与正式仿真一致的字段映射。
- **回归步骤**：以 `source.wavelength_nm=780`、不提供顶层 `wavelength_nm` 的项目生成至少 1 个 Headless 样本；检查生成样本的特征 `wavelength_nm` 和引擎请求均为 780 nm。再改为 808 nm 重复一次，确认不会继续使用 780/1550 的旧值。
- **通过标准**：数据集特征、正式求解输入和当前方案波长一致；任何字段缺失不得静默换成另一个实验波长。
- **优先级**：P0（会污染模型、SHAP和后续诊断）。

## ML-STATE-002：重启后不得把“当前模型”忘掉或擅自换成最近模型

### 风险

“设为当前模型”是用户明确研究决策。如果关闭/重新打开平台后无条件清空，用户容易误以为旧模型仍在使用；更危险的是把最近训练模型或列表第一项自动当作当前模型。

### 修复要求

- 只持久化用户明确采用的 `current_model_id` / `current_dataset_id`；
- 新训练模型仍只记为“最近模型”，不能自动覆盖当前模型；
- 启动后必须等 registry 确认 ID 仍存在才恢复；
- 已删除/损坏/不存在的 ID 清空，不得回退到列表第一项。

### 回归步骤

1. 显式采用模型 A，关闭并重新打开平台；registry 加载完成后应恢复 A。
2. 训练模型 B 但不点击“设为当前模型”，重启后仍应是 A。
3. 删除 A 后重新启动，当前模型应为空并提示重新选择，而不是自动变成 B。

### 通过标准

当前模型只来自用户明确采用且仍存在的模型；“最近模型”和“当前模型”始终是两个状态。

## AI-DIAG-001：AI 必须能从真实后台扫描结果提取曲线特征

### 风险

AI 如果只认识前端已经整理成 `parameter_response` 的绘图字典，而不认识后台真实的 `parameter_grid/response_values`，不同页面给它的上下文形式稍有变化就会退化成泛泛解释。

### 回归步骤

1. 直接把真实 `/scan/jobs` 结果（`parameter_grid + response_values`）交给诊断器。
2. 确认能得到峰位、峰高、3 dB 宽度、对称性。
3. 若峰位偏移同时明显不对称，不允许只下“零点偏差”单一结论，应提示参数耦合/二维扫描等区分手段。
4. 确认最后只给“优先检查方向 + 验证方法”，不把扫描或 SHAP 写成实验因果。

### 通过标准

前端绘图数据和后台原始扫描结果两种形式得到一致的曲线观察逻辑；诊断遵守“现象 → 优先检查 → 为什么 → 怎样区分 → 怎么验证”。

## PERF-CACHE-001：预制 SHAP 缓存解压 ZIP 后必须仍然有效

### 曾发生的问题

预制 SHAP 缓存原先把模型/数据文件的 `mtime_ns` 直接写入缓存键。工作目录中测试可以命中，但最终 ZIP 重新解压后文件时间戳发生变化，导致**同一内容的第一条 SHAP 请求仍然重新计算**。

### 根因

文件时间戳适合运行时快速失效判断，但不是跨复制、跨 ZIP 解压的稳定内容标识。

### 修复要求

- 持久 SHAP 缓存键使用模型、预处理器、manifest、数据集 manifest 与 samples 的**内容摘要**；
- 运行进程内部可以用 `(路径, 大小, mtime)` 缓存内容摘要，避免每次重复哈希；
- 文件内容变化必须产生新摘要并失效旧 SHAP；
- 仅时间戳变化而内容不变时，跨 ZIP/复制后的缓存仍应命中。

### 回归步骤

1. 用最终演示数据和模型计算一次 SHAP，并保存预制缓存。
2. 打完整 ZIP。
3. 解压到全新目录；使用全新 `USER_DATA_DIR` 启动后端。
4. 不预先请求 SHAP，直接发送与预制缓存完全相同的第一条解释请求。
5. 检查返回 `cache_hit=true`、`elapsed_ms=0`。
6. 修改模型 manifest 或数据样本内容后重复请求，确认不能命中旧缓存。

### 通过标准

最终 ZIP 解压后的**第一次相同 SHAP 请求**直接命中预制缓存；改变真实内容后缓存可靠失效。
