# 优化配置、正式任务和候选回写（2026-10-01）

分支 `js`；整个迁移计划仍未完成。

## 已接通的流程

- 优化变量来自当前项目的原版变量目录，选择、编辑范围、评价方式、目标、工程和准直约束均进入原有优化接口。
- `/optimization/presentation` 和 `/optimization/prepare` 使用共享的纯 Python 展示与请求逻辑；保留原有光学引擎和优化器。Simulation 的导入复场选项随请求传递。
- Pinia 保存配置、变量、任务编号和提交时项目签名；任务完成后读取实际结果，刷新后恢复。项目变化时限制旧候选回写。
- 候选表使用原版的格式和变量映射。应用方案原子更新项目，提交正式 Simulation，按原版跳转到光纤耦合页面，并在优化结果中显示验证状态。验证任务与来源优化任务关联并持久化。
- 相同物理值不再因编辑器元数据变化被误判为新方案。应用前结果已过期时，不将它作为改善幅度的基线。
- 图表数据、线图/柱图和高对比轴样式从原版提取为共享函数；后端输出 SVG 展示内容，没有在 JavaScript 中计算光学指标。

## 修正的原有接口问题

1. 原版请求先写工程约束，随后覆盖整个 `opt_options`，导致控件值未进入计算；现在统一写入最终选项。
2. 工程约束读取旧表面字段，但候选系统使用 DTO 的 `distance_to_next_mm`、`material_after`、`clear_aperture_mm`；加入字段兼容。末表面不存在后续传播段，其零距离不作为空气间隔。
3. 控件允许最高100000次评价，API迭代上限5000。保留完整评价预算，同时限制迭代参数；实际 prepare 返回5000/100000，不宣称已执行这么大的任务。

截图在 `tests/golden/ui-{baseline,current}/optimization/`：原版8种状态；当前采集选中变量、更多参数、模型辅助、准直展开、过程曲线和候选柱图。两端完成图使用同一份 `formal-job-result.json`。
